# C&C Stage Images

Generate FAR, MID, GROUND, OBJECT_ATLAS and FLYING directly with the built-in image-generation tool, one call per asset, one agent, in that order. Follow Generate → identify issues → apply corrections → verify → deliver five PNGs. Use the bundled pixel-finishing script for mechanical corrections under the user-authorized process; do not request permission again for preserving pixels and moving them within the canvas. Complete all five requested assets without waiting for per-image approval. For a single-image request, generate only that image. Preserve existing artwork unless replacement is explicitly requested.

## Prepare the artwork brief

Use the user's supplied stage brief and applicable rules. For repository-backed requests, read mandatory repository instructions and only the selected stage's current brief, filenames and relevant source geometry. In claudejones/candcgame these are in config/remaining-continent-proposal.json, the stage catalog/registry, and the relevant production specification. Do not run the asset-command resolver, recover old jobs, read publication history, inspect upload credentials or start CI as part of inline generation. If a required subject selection is missing, resolve that specific selection; do not invent approval. Use provided approved style/location/species reference images when available; never claim an unattached reference was used.

Review each image prompt before generation. Keep it limited to the image's subject, pixel-art style, palette, composition and applicable geometry. Use consistent visible square pixel clusters and limited colors across all five. Plan FAR and MID as a layered composition: place distant identifying features where they will remain readable behind MID at the established rendering scales. Give MID varied heights and meaningful transparent sightlines appropriate to the stage; avoid a continuous tall wall that hides the distant scene. Carry these constraints into both prompts, and inspect FAR before composing MID. Avoid workflow instructions inside image prompts. Do not assume a prompt's numerical request guarantees the output dimensions.

Keep a distinct gameplay lane in the composition. Put decorative animals and other obstacle-like MID details visibly behind the running surface, on their own supported terrain, using appropriate smaller apparent scale and restrained contrast. Do not place their feet, bodies or shadows on the gameplay contact line or make them look like collidable hazards. Carry this requirement into MID and GROUND prompts; preserve natural biome detail rather than requiring a blank background.

## Image rules

Use the current selected stage contract where it differs from these established defaults:

- Canvas: 2172×724. FAR opaque; the other four actual RGBA transparency, no painted checkerboard, labels, guides or UI.
- FAR: selected distant landmark, recognizable silhouette away from horizontal joins, restrained distant scale, matching repeat edges; no foreground hazards.
- MID: selected middle-distance scenery and restrained local details; transparent sky openings, no duplicated FAR landmark or baked sky; lower scenery extends to canvas bottom without a gap. Authored source anchor Y621; matching horizontal joins.
- GROUND: side elevation, perfectly level walking surface at source row393. Above the surface transparent, below opaque to bottom. No slopes, perspective vanishing point, scenery props or hazards. Match height and texture across repeat edges.
- OBJECT_ATLAS: two 1086×724 cells, one approved static object per cell, complete characteristic silhouettes; contact anchor at local (543,620) in each cell; at least 32px empty gutter at cell boundaries. Preserve natural proportions rather than filling the cell.
- FLYING: four 543×724 cells in one row, approved species/count. Right-facing throughout; stable body size and local anchor(271,362). Explicit poses: raised apex, descending diagonal, lowered apex, rising diagonal. All four wing silhouettes visibly distinct. For flocks each bird must animate and remain readable. Keep all appendages within their cell with 32px clear gutters.

Y=0 means zero added visual offset, not that MID/GROUND are drawn at canvas-top zero. Renderer mapping is `drawY = targetAnchorY - sourceAnchorY * scale + visualOffsetY`. Preserve FAR/MID/GROUND offsets0 and scale multipliers1.25/1/1. Do not change these to hide incorrect source artwork.

## Identify issues, apply corrections and verify

After each generation, measure actual dimensions/transparency and inspect the relevant image geometry. Identify the MID baseline, the ground surface, actual object contacts or the same stork torso feature in each frame. Do not infer a contact point from the lowest nontransparent pixel or a body anchor from a changing wing silhouette.

Identify issues in two categories before correcting them:

- **Geometry:** dimensions, transparency, measured anchors, gutters, clipping and animation alignment. Use the pixel script for supported measured corrections.
- **Visual composition:** stage identity, consistent style/palette, FAR visibility behind MID, readable depth, clear separation of decorative scenery from the gameplay lane, repeat joins, and distinct animation poses with stable body proportions. Correct artwork through a focused image edit when pixel placement cannot solve it. For a new generation task, revise only the failing candidate; for previously accepted artwork, stay within the requested revision scope.

Once FAR and MID exist, inspect them together at canonical scale and zero added offsets before generating the remaining assets. Use the current ground/surface guide if GROUND is not generated yet. Compare FAR alone with FAR+MID at the start, middle and end of the stage, plus any obvious worst overlap/repeat position, using the actual parallax settings. Recognizable distant scenery must remain readable across those views; visible sky alone is not a pass. A landmark may be partly occluded naturally, but MID must not erase the stage's distant identity or depth. Do not impose a universal building height or transparent-area percentage on every biome. If settings differ from the contract, correct the settings first; if canonical placement hides FAR, diagnose the artwork composition. Do not lower MID below its baseline, shift editor offsets, or erase opaque buildings as transparency cleanup to force a pass.

At the same sampled scroll positions, inspect the combined scene with available approved character and stage hazard sprites at their established display sizes and anchors. Check that their silhouettes remain readable against MID and that decorative animals/props appear supported on a separate background plane, not standing on the running surface. Natural background overlap is acceptable; ambiguous gameplay objects and competing silhouettes are not. Use quieter texture, tonal separation and supported background placement rather than shifting editor offsets. If runtime sprites/settings are unavailable, use clearly labeled scale guides and report this check as provisional; do not claim a verified gameplay composite. A numeric clearance alone is not proof of perceptual separation.

Record each issue briefly as asset, observed defect, chosen correction, and verification. Revise the affected prompt with the diagnosed composition requirement before an artistic correction. Recheck the failing view and the other sampled positions after the correction. If one focused artistic correction leaves the same issue unresolved, preserve the candidates and report the specific blocker instead of automatically regenerating in a loop.

Use `scripts/finish_pixels.py` for exact canvas placement and integer translations. Read [pixel-finishing.md](references/pixel-finishing.md) when creating the correction plan. This is the user's authorized pixel-editing workflow; use the image generator for artistic changes, not numerical alignment retries. Preserve originals. The helper verifies source hashes, prevents clipping and overlapping cells, requires gutters, and checks saved PNG bytes. The user has authorized routine measured bottom-margin trims, faint-alpha cleanup, terrain opacity normalization and one uniform animation scale as part of this process. Record them in the correction plan; do not request approval again for those operations within the documented bounds. Never crop a character, bird, object or landmark, stretch proportions, use different scales per flying frame or invent missing scenery. Escalate only a change beyond this scope. Do not relax source requirements or editor offsets to manufacture a pass.

Check the final combined landscape again at the same sampled positions with established anchors and visual offsets0, alongside repeat joins and the flying cycle. The combined-landscape pass requires correct grounding, readable FAR/MID depth and a visually distinct gameplay lane; a gap-free seam alone is insufficient. Include the reviewed scroll positions, visible distant features and whether character/hazard readability was checked with actual sprites or provisional guides in the concise report. A geometry pass does not establish visual correctness or anchor identity. Keep a concise result per image, reuse passing outputs, and correct only a diagnosed remaining defect. No full software regression suite, coordinator state, upload preflight, CI or gameplay simulation belongs in this process. Do not repeat a failed image-generation attempt to fix an exact pixel coordinate.

Display generated results inline and return original-byte downloads of the finished PNGs. If an image does not display, link the existing file rather than generate it again. Use canonical filenames in a separate output directory, preserve the originals, and save deliverables using the environment's file facilities. Do not describe a partially blocked set as import-ready.

Deliver one ZIP containing exactly the five corrected PNGs under their canonical names, plus the stage ID and a separate concise measured/visual report. Use the helper package command after reviewing exact output hashes. Do not zip blocked candidates as a completed set. Workbench owns hashes, metadata, frame regions, import settings, handoff JSON and calibration. The user need not prepare these. Do not upload, integrate or deploy unless separately requested.

When the set passes, provide: "Import these five PNGs for <STAGE>. Prepare the metadata, starting settings and Workbench import, then continue calibration." Substitute the actual stage. If blocked, give the exact remaining failure. Candidate import for arbitrary dimensions/anchors is not available unless its implementation is verified.
